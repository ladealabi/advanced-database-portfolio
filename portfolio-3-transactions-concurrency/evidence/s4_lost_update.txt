SCENARIO: CONCURRENCY PROBLEM: lost update, and three ways to prevent it
==============================================================================
A naive application reads the balance, subtracts in application code, then
writes the result back. Two ATM withdrawals (N10,000 by A and N20,000 by B)
run at the same time against Ada's N50,000. Correct final balance: N20,000.
Part 1 shows the anomaly: B overwrites A's update. Part 2 prevents it with
pessimistic locking (SELECT ... FOR UPDATE). Part 3 uses REPEATABLE READ,
where PostgreSQL detects the conflict and aborts B, which must retry. Part 4
uses an atomic UPDATE balance = balance - x.
